Contributor submission contract

  1. The public page helps a contributor describe the submission: chosen stage, contribution type, scripture/edition or other source, passage, rights/provenance notes, contributor credit name, related artifacts, prompt, evidence links, and priority.
  2. Contributors must provide material or links that are publicly accessible without a login. Private Drive files, permission prompts, and restricted materials are rejected by the intake validator; sharing a link does not establish rights or scholarly authenticity.
  3. A GitHub issue is an intake and discussion record, not acceptance. Issue attachment upload or a public file URL does not itself put the material into the canonical project tree.
  4. Maintainers preserve the received bytes, calculate a SHA-256 digest, request an OpenTimestamps receipt for those exact bytes, and respond with the issue/reference and timestamp status before any transformation or merge. A pending OTS calendar receipt is not yet a verified timestamp.
  5. Accepted repository changes are reviewed through a pull request. The project account may prepare a branch/PR after intake; issue submission never auto-merges or grants authorship beyond the contributor's stated credit.

Two contributor routes

1. Pull request (contributors with GitHub access)

Contribute to the project repository using a branch and PR with the relevant source files, images, rights/provenance notes, and traceability references. Link the PR in the intake issue. Review and merge remain maintainer-controlled.

2. Public-link handoff (no GitHub account)

The intended route is a simple public form that accepts the contributor's name/credit, submission details, and public file URLs. A project-owned intake service must validate public access and file type/size, create a GitHub issue using a server-side GitHub App identity, preserve and hash the original files, request OTS stamps, and return the new issue number and status to the contributor.

Deployment status: this account-free intake service is not connected yet. GitHub Pages is static and cannot create an issue or upload files on a visitor's behalf. Do not represent the current GitHub issue link as account-free; submitting there requires a GitHub account. Do not put a GitHub token in browser JavaScript.

Project and storyboard utility

  • One shared registry entry in workflow/project_registry.json identifies one project and its source repository, branch, and optional asset path. Projects are not forced into one monolithic repository; maintainers add entries after review.
  • A story segment is a verse, stanza, paragraph, or another user-defined text unit. Its storyboard is an ordered list of keyframes: first/start, any number of intermediate frames, and last/end.
  • Each keyframe has an optional public asset URI or local file reference, a visual description, and frame-specific instructions. A provider prompt includes all ordered references and continuity constraints.
  • The current front end reads the shared registry, public GitHub repository image trees, or a CORS-enabled public JSON manifest for other hosts. A new project form prepares a registration issue; its local draft can be exported, but only a reviewed maintainer change updates the shared registry.
  • A public video/project URL can be shared through platform share intents. Social platforms handle their own final post; Instagram requires a manual app upload.

Limits: a registration request is not automatically merged into the shared registry. Arbitrary repository writes, authenticated/private repository browsing, provider-side image uploads, video uploads, and automatic social posting require separate authenticated services and are not claimed by this static tool.

Required intake service behavior

  • Accept only unauthenticated-public HTTPS links; reject login-only or access-denied links with a plain-language explanation, without trying to bypass access controls.
  • Fetch from a controlled backend with size/time/type limits, safe redirect handling, and SSRF protections; do not make the browser upload private files or expose credentials.
  • Create a labeled contribution issue through a GitHub App or equivalent server-side identity. Record contributor name as self-reported, not identity-verified.
  • Store exact received bytes or an immutable public source reference; calculate SHA-256 and request OTS stamping before normalization, conversion, or editing. Return the hash, OTS status, and issue link to the contributor.
  • Reject and explain non-public/inaccessible evidence, failed downloads, unsupported content, and malformed metadata. Never claim a file was timestamped or received when it was not.
  • Never merge or publish automatically. Maintainers review rights, source lineage, content, and proposed artifact changes; accepted work goes through PR and CI.

Current hosted issue routing is implemented in .github/workflows/pillar6q-workflow.yml. It routes an issue after it exists; it does not supply the missing anonymous intake endpoint, fetch evidence URLs, or create OTS receipts.
